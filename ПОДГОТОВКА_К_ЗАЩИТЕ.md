# Шпаргалка к защите ЛР № 2 и № 3 («Автостоянка»)

## 1. Суть за минуту

**ЛР № 2.**
- Прототип из трёх микросервисов на Node.js:
  - **auth** — вход и пользователи;
  - **clients** — клиенты и машины;
  - **parking** — места, тарифы, въезд/выезд, оплата.
- У каждого сервиса своя база в PostgreSQL. Общаются по REST.
- Вход по JWT, две роли: оператор и администратор.
- CRUD во всех сервисах сделан одной общей функцией `crudRouter` — это DRY.
- Пример из ЛР № 1 считается точно: 360 + долг 150 = **510**, оплата 500 → долг **10**.

**ЛР № 3.**
- **Тесты:** 28 штук — 15 модульных с заглушками и 13 интеграционных на живых контейнерах. Все пройдены.
- **Журнал:** JSON с `requestId`, общим для всех сервисов.
- **Метрики:** `GET /metrics`, проверка доступности — `GET /health`.
- **Нагрузочный тест на 500 000 записей:**
  - средняя нагрузка — 30 запросов/с, p95 ≤ 0,4 с;
  - пик — 105 запросов/с, p95 до 1,4 с;
  - узкое место — **база данных** (≈ 11 ядер из 12), таблицы читаются целиком.
- **Предложения:**
  - индексы — проверено: запросы в 30–40 раз быстрее;
  - несколько копий сервисов;
  - бэкапы с WAL;
  - резервный сервер БД;
  - мониторинг.

## 2. Демонстрация

Перед сдачей:
```bash
cd ~/projects/architecture/parking-system
docker compose down -v && docker compose up -d --build     # подождать ~1 мин
docker compose ps                                           # сервисы (healthy)
```

**ЛР № 2** — браузер, http://localhost:8080:
1. Вход `operator` с неверным паролем → 401. Потом `operator / operator123`.
2. «Стоянка»: ввести `А123ВС777` → подтягиваются владелец и скидка 10 %. Этот запрос идёт в clients-service.
3. Время въезда 23.09.2026 08:40 → «Зарегистрировать въезд»: место на плане стало красным.
4. «Выезд», время 13:05 → расчёт: 265 мин → 5 ч → 400 → −10 % = 360 → + долг 150 = **510**. Оплатить 500 → долг **10**.
5. «Администрирование»: пользователи → **403** (запрещает сервер, а не интерфейс).
6. Выйти, войти `admin / admin123` → пользователи видны, можно создать.
7. В терминале: `npm run demo` → «шагов 16, ошибок 0». Запускать **до** тестов: демо нужна чистая база.

**ЛР № 3** — терминал:
```bash
npm test                    # 15 модульных, ~1 с
npm run test:integration    # 13 интеграционных, ~10 с (в одном тесте останавливается clients-service)
curl -s localhost:3003/metrics | head -c 600
curl -s localhost:3002/health
docker compose logs --no-log-prefix parking-service clients-service | grep car_entry   # журнал
```
Нагрузочный тест живьём не запускай: результаты есть в отчёте (таблицы и график).

## 5. Вопросы по ЛР № 2

**Почему микросервисы?**
В ЛР № 1 требуются модульность, REST и масштабирование до 5 площадок. У частей разная нагрузка: въезд/выезд идут постоянно, клиенты меняются редко. Честно: для одной стоянки монолит был бы проще.

**Почему у каждого сервиса своя база?**
- Плюс: сервис меняет свою схему, не ломая другие.
- Минус: нет внешних ключей и общих транзакций между базами — целостность проверяет сервис.
- Сервер PostgreSQL один — это проще (KISS).

**Как сервисы общаются?**
По REST в формате JSON. При въезде и выезде parking-service спрашивает у clients-service владельца и скидку (`GET /api/cars/by-plate/{номер}`). Передаётся **токен пользователя**, поэтому clients-service сам проверяет права. Если clients-service не отвечает 2 с — ответ 502, а остальные функции продолжают работать.

**Почему REST, а не очередь или gRPC?**
Ответ нужен сразу (чья машина, какая скидка), и REST требовался в ЛР № 1. Очередь подходит для событий «отправил и забыл», gRPC — лишняя сложность.

**Как работает CRUD-фабрика?**
`crudRouter(pool, { table, schema, read, write, filters, columns, prepare })` создаёт GET-список, GET по id, POST, PUT и DELETE.
- `schema` — какие поля можно присылать (остальные отбрасываются);
- `read` / `write` — роли для чтения и изменения;
- `prepare` — хук перед записью (хеширование пароля, приведение номера к единому виду).

Все значения передаются параметрами `$1, $2`, поэтому SQL-инъекции невозможны.

**Чем модель отличается от ЛР № 1?**
1. Сотрудник, Оператор и Администратор — одна таблица с полем `role`.
2. Скидка — процент у клиента.
3. Между базами нет внешних ключей.

Задолженность не хранится, а вычисляется представлением `session_balances`: стоимость минус оплаты.

**Как запрещён повторный въезд?**
Сервис проверяет, есть ли открытая стоянка, плюс в БД есть уникальный частичный индекс `(car_id) WHERE exit_time IS NULL`.

**Как распределяется оплата 500 ₽?**
Сначала гасится самая старая стоянка (долг 150), потом текущая (350 из 360). Остаток 10 становится долгом. Всё выполняется в транзакции с блокировкой стоянок клиента.

**Как устроен JWT?**
Заголовок, данные (`id`, `login`, `role`, срок) и подпись секретным ключом. Токен можно прочитать, но нельзя подделать. Каждый сервис проверяет подпись сам, без обращения к auth-service.

**401 и 403?**
401 — «не знаю, кто ты» (нет токена или он неверный). 403 — «знаю, но тебе нельзя».

**Почему оператор видит кнопки, которые ему запрещены?**
Специально: проверку делает сервер. Скрытая кнопка не защищает — запрос можно отправить curl'ом.

**SOLID / DRY / KISS:**

| Принцип | Где в проекте |
|---|---|
| S | сервис = одна область; `domain.js` — расчёты, `parking.js` — операции, `clientsApi.js` — вызов соседа |
| O | `crudRouter` расширяется параметрами без правки кода |
| L | вместо `clientsApi` можно подставить заглушку с тем же методом |
| I | маленькие отдельные функции: `authenticate`, `authorize`, `validate` |
| D | `createParking(pool, clientsApi)` получает зависимости параметрами |
| DRY | одна CRUD-фабрика на 6 ресурсов, общий код в `common`, один Dockerfile |
| KISS | REST, один PostgreSQL, SQL без ORM, запуск одной командой |

## 6. Вопросы по ЛР № 3

**Модульный и интеграционный тест — в чём разница?**
Модульный проверяет модуль без БД и сети: вместо них заглушки. Пример — CRUD-фабрика с фейковой БД, которая запоминает SQL. Интеграционный работает с настоящими сервисами и базой. Пример — сценарий 510/10 или остановка clients-service → 502.

**Как интеграционные тесты можно запускать повторно?**
Каждый тест создаёт свои данные: случайные номера, новых клиентов.

**Какие ошибки нашли?**
1. **nginx запоминал старый IP сервиса** → 502. Исправлено: адрес определяется через DNS Docker.
2. **Контейнер останавливался 10 с:** Node.js как PID 1 игнорировал сигнал. Исправлено: `init: true`.
3. **Нагрузочный скрипт сам себя тормозил** (синхронный `docker stats`). Исправлено.
4. **БД — узкое место.** Предложены индексы.
5. **Токен заблокированного пользователя действует до 8 ч.** Предложены короткие токены.

**Что пишется в журнал?**
Каждый запрос (адрес, код, время, пользователь), создание/изменение/удаление записей, въезд, выезд, оплата, входы, отказы, ошибки, недоступность clients-service, медленные запросы к БД (> 200 мс). Формат — одна строка JSON.

**Как связать записи разных сервисов?**
nginx присваивает запросу ID (заголовок `X-Request-Id`), parking-service передаёт его в clients-service, и оба пишут его в журнал.

**Какие метрики собираются?**
- время ответа по каждому маршруту (среднее, p95, максимум);
- одновременные запросы (текущее и максимум);
- память (текущая и пик);
- время запросов к БД по таблицам.

Загрузку процессора давал `docker stats`.

**Что такое p95 и почему не среднее?**
p95 — время, в которое укладываются 95 % запросов. Среднее прячет медленные запросы.

**Как искали узкое место?**
1. CPU PostgreSQL ≈ 1100 %, а сервисы загружены ≈ 20 %.
2. В метриках больше всего времени у запросов к `parking_sessions` и `session_balances`.
3. `EXPLAIN ANALYZE` показал: поиск по номеру читает всю таблицу, а долг читает всю таблицу оплат (нет индекса на `payments.session_id`).

**Почему даже «план мест» медленный на пике?**
Он ждёт свободное соединение с БД, а все соединения заняты медленными запросами.

**Что предлагаешь?**
1. **Индексы** — проверено: в 30–40 раз быстрее.
2. **Несколько копий сервисов за nginx:** сервисы не хранят состояние, пользователь «живёт» в JWT.
3. **PgBouncer и реплика БД для чтения.**
4. **Кэш и circuit breaker** для вызова clients-service.

**Бэкапы?**
- Ежедневно `pg_dump` трёх баз, 14 копий вне сервера.
- Архив WAL — восстановление на любой момент, чтобы терять не больше одной транзакции (требование ЛР № 1).
- Раз в месяц пробное восстановление с прогоном тестов.
- Резервный сервер PostgreSQL — ради доступности 99,5 %.

**Проверка доступности?**
`GET /health` проверяет, что сервис отвечает и видит свою базу (200 или 503). Docker опрашивает его каждые 10 с и перезапускает упавший контейнер. Предложено добавить внешний опрос с оповещением.

## 7. Неудобные вопросы

| Вопрос | Ответ |
|---|---|
| Где блокировка после 5 попыток (ФТ-3), личный кабинет (ФТ-20)? | В прототип вошли основные функции; эти требования среднего/низкого приоритета — для следующих версий |
| Заблокировали пользователя, а он работает? | Да, до конца срока токена (≤ 8 ч) — ограничение JWT; решение — короткие токены + токен обновления |
| Удалили клиента — а стоянки? | Остаются: внешних ключей между базами нет. Решение — «мягкое» удаление или событие через брокер |
| Нет HTTPS? | В прототипе нет; в эксплуатации TLS настраивается на nginx |
| Нагрузка шла с того же компьютера? | Да, это погрешность, но узкое место (БД) видно однозначно |
| Почему демо второй раз падает? | Оно рассчитано на чистую базу (`docker compose down -v`); интеграционные тесты — повторяемые |

## 8. Если что-то сломалось

| Симптом | Что делать |
|---|---|
| 502 в интерфейсе | `docker compose ps` — все ли healthy; подождать 10 с или `docker compose restart frontend` |
| Демо падает | `docker compose down -v && docker compose up -d --build`, подождать, запустить снова |
| Тест упал сразу после запуска | сервисы ещё не healthy — подождать и повторить |
| `npm run load` даёт 404 | сначала загрузить `scripts/volume.sql` |
| Нужно вернуть как было | `docker compose down -v && docker compose up -d --build` |
